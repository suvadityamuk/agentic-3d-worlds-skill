# Privacy and training suitability

Public runs are identified only by a short descriptive title. Do not publish user or account names, personal email/phone/address data, local usernames/paths, source chat links, run/thread/session/message/tool/project/deployment identifiers, source commit references, or exported file-checksum inventories. Do not embed them in titles, filenames, trace text, JSON keys, comments, screenshots, archives, or supporting reports.

Use the public schema allowlist. Keep only task-relevant visible dialogue and observable operations needed to explain the resulting world. Remove host wrappers, unrelated environment inventories, credentials, system/developer instructions, hidden reasoning, and compaction summaries. Pair tool results through sequential step positions. Keep the final geometry, appearance, materials, lighting, behavior, relevant code, failures, and factual limitations useful for later training.

The helper removes common identifiers and personal-data patterns and strips identity fields from structured JSON. Supply known contributor names, handles and other sensitive strings through an agent-created private JSON terms file outside the run using `--private-terms-file`. This file, integrity sidecars, approval digests, and submission receipts stay local. Never copy the private mapping into a report.

Regex checks cannot establish absence of all personal information. Review names and narrative context, filenames, URLs, attachments, and public-facing descriptions manually. Public landmark names, geometry coordinates, library names and required source attribution are useful non-personal data. Package dependency integrity values are executable dependency metadata, not identities of people or runs; preserve valid lockfiles. All publication-specific hashes stay outside training records.

Inspect binaries, screenshots, EXIF/document metadata and archive contents with appropriate tools. If an artifact cannot be inspected, omit it with a limitation. If removing an identifier would break a model or program, replace the dependency with a meaningful semantic relationship and test it; do not publish a broken artifact or retain the private identifier. For example, deduplicate map shapes using their coordinates rather than an upstream record ID. Clean hosting configuration and reference strings as well as text metadata.

Before a new contribution, show the cleaned title, task, artifact names, counts, redactions, limitations and public destination, then obtain confirmation. Existing explicit requests to remove identifying data from an already approved publication authorize that cleanup; do not ask for redundant confirmation. Normal contributions use PRs. Owner-authorized maintenance may update the affected dataset files and descriptions and remove superseded references. The Hub itself displays account and Git/PR metadata; do not copy platform identity metadata into training files or claim it can all be eliminated by a skill.
